    모델 검증과 모니터링¶

    1.1 검증의 목적¶

    모형을 만드는 것과 쓸 수 있다고 판단하는 것은 다른 문제다. 검증은 모형이 실전에서도 안정적으로 작동할 것이라는 근거를 확보하는 과정이다. 학습셋에서만 성능이 좋은 멍청한 모형을 걸러 내고, 학습·검증·OOT 어디서나 안정적인 똑똑한 모형인지 확인하는 일이다.

    단계 질문 도구
    개발 중 Train 대비 Valid 성능 차이는? CV, Hold-out
    개발 완료 미래 데이터에서도 통하는가? 확률이 맞는가? 설명이 상식적인가? OOT 검증, 캘리브레이션, 이 페이지의 ML 특화 검증
    운영 중 모형이 여전히 유효한가? PSI·CSI, 성능·캘리브레이션 모니터링

    전통 스코어카드와 ML 모형은 검증의 뼈대(변별력, 안정성, 캘리브레이션, OOT, 모니터링)가 같다. 공통 프레임워크는 스코어카드 섹션에서 다루고, 이 페이지는 ML 모형이라서 더 봐야 하는 것에 집중한다.

    참조

    • 데이터 분리(Train/Valid/Holdout/OOT, 층화추출, 고객 단위 분할): 데이터 분리 전략
    • 변별력 지표의 정의와 계산: 모형 성능 평가: KS · AR · Gini
    • OOT 검증 절차와 허용 하락폭: OOT 검증
    • PSI·CSI, Back-testing, 리캘리브레이션·재개발: 모형 모니터링과 운영

    1.2 변별력 지표¶

    변별력은 KS와 AR로 본다. 정의와 계산 예시는 모형 성능 평가에 있고, 여기서는 ML 모형을 평가할 때의 주의점만 정리한다.

    지표 정의 단위 ML 모형에서의 주의점
    KS Good과 Bad의 누적 점수 분포 간 최대 차이 %p (0~100) 동점 점수는 묶어서 누적해야 한다(아래 참조)
    AR CAP 곡선 아래 면적 기반의 정확도 비율. AR = Gini = 2·AUC − 1 소수 (0~1) AUC(ROC 면적)와 1:1로 대응하는 같은 정보다. AUC로 계산했다면 AR로 환산해 보고한다
    CAP 곡선 고위험(저점수)부터 차례로 선발할 때 누적 Bad 포착률을 그린 곡선 곡선 "하위 10%로 Bad의 몇 %를 잡는가" 같은 운영 질문에 바로 답한다. AR은 이 곡선을 한 숫자로 요약한 것

    동점 점수는 묶어서 계산한다

    KS와 AR은 점수 순서로 누적 분포를 만들어 계산한다. 점수가 같은 고객들을 행 단위로 하나씩 누적하면, 동점 안에서 Good과 Bad가 어떤 순서로 정렬되었느냐에 따라 값이 달라진다. 예를 들어 동점 집단 안에서 Bad가 먼저 정렬되면 KS·AR이 부풀려진다. 동점 점수는 한 구간으로 묶어 누적해야 한다. 수백 개 트리를 합산한 ML 점수는 거의 연속값이라 동점이 드물지만, 트리 수가 적거나 깊이가 얕은 모형, 점수를 정수로 반올림해 등급화한 경우에는 동점이 많아진다.

    변별력이 지나치게 높으면 누수를 의심한다

    신청 시점 정보만 쓰는 신청평점(ASS)에서 OOT AR이 비현실적으로 높게 나오면(예: AR 0.8, AUC로 0.9 수준) 먼저 데이터 누수(Leakage)를 의심한다. 관측 시점 이후에야 알 수 있는 정보(예: 성과 기간 중의 연체일수, 사후에 갱신된 변수)가 학습 변수에 섞였는지 점검한다. 다만 최근 연체 이력이 핵심 변수인 행동평점(BSS)에서는 높은 변별력이 정상일 수 있으므로, 수준 자체보다 "그 정보가 관측 시점에 정말 알려져 있었는가"를 확인하는 것이 본질이다. 용도별 KS·AR 벤치마크는 모형 성능 평가를 따른다.

    1.3 OOT (Out-of-Time) 검증¶

    OOT 검증의 개념, 샘플 설계, 확인 항목, 허용 하락폭 기준, 성능 급락 시 대응은 스코어카드 섹션의 OOT 검증을 그대로 따른다. ML 모형이라고 별도 기준을 두지 않는다. ML 모형은 학습셋 성능이 높아 OOT 하락폭이 커 보이기 쉬우므로, 개발 대비 하락폭과 함께 같은 OOT에서의 스코어카드(챌린저 비교) 대비 수준을 반드시 같이 본다(1.4절).

    ML 모형에서 OOT 단계에 추가로 확인할 사항은 다음과 같다.

    항목 무엇을 보는가
    과적합 신호 학습 → 검증 → OOT로 갈수록 성능이 계단식으로 떨어지는가. 학습셋과의 격차가 기준선 모형보다 유독 큰가
    기여도 구조의 안정성 개발 데이터와 OOT에서 SHAP 중요도 순위·방향이 유지되는가 (1.4.6)
    캘리브레이션 OOT에서 등급별 예측 PD와 실현 불량률이 맞는가 (1.4.1)
    재현성 같은 데이터·설정으로 다시 학습하면 같은 모형이 나오는가. 시드, 결정적 옵션, 라이브러리 버전, 실행 환경을 고정·기록했는가

    1.4 ML 특화 검증 항목¶

    1.4.1 확률 캘리브레이션¶

    변별력(KS·AR)은 순서만 본다. 점수를 어떤 단조 변환으로 바꿔도 KS·AR은 그대로다. 반면 한도·금리·충당금·자본 계산은 확률(PD) 자체를 쓰므로, 예측 확률이 실제 불량률과 맞는지(캘리브레이션)를 따로 검증해야 한다.

    ML 모형의 출력 확률은 여러 이유로 어긋나기 쉽다.

    • Random Forest: 트리 투표의 평균이라 극단 확률(0이나 1에 가까운 값)이 잘 나오지 않고 중간으로 몰리는 경향이 있다
    • 불균형 보정: Bad를 과대 표집(oversampling)하거나 Bad에 가중치를 주면, 순서는 유지되어도 확률 수준이 통째로 올라간다
    • 표본 설계: 개발 표본의 불량률이 운영 모집단과 다르면(기간 선택, 거절자 제외) 수준이 어긋난다
    • 과적합: 깊은 트리·많은 라운드는 학습셋에서 확률을 0과 1 쪽으로 밀어붙여, 새 데이터에서는 과신(overconfidence)한 확률이 된다

    점검 방법

    1. 등급(또는 점수 구간)별 비교표: 구간마다 평균 예측 PD와 실현 불량률, 건수를 나란히 놓는다. 가장 기본이고 가장 설득력 있는 산출물이다
    2. 캘리브레이션 곡선: x축 예측 PD, y축 실현 불량률. 대각선에 가까울수록 잘 맞는다
    3. 구간별 이항 검정: 각 등급의 실현 불량 건수가 예측 PD 기준 이항분포에서 나올 만한 수준인지 검정한다
    4. 전체 적합도 검정(Hosmer-Lemeshow 등)은 표본이 크면 사소한 차이도 유의하게 나오므로, 단독 판정 근거로 쓰지 않고 비교표와 함께 본다

    보정 방법

    캘리브레이션이 어긋나면 순서는 그대로 두고 확률만 고친다. 모형 점수를 입력으로 한 로지스틱 회귀(Platt scaling)나, 단조 계단 함수를 맞추는 Isotonic Regression이 대표적이다. 보정 함수는 모형 학습에 쓰지 않은 별도 데이터로 적합하고, 보정 후 결과는 다시 OOT에서 확인한다. 단조 변환이므로 KS·AR은 변하지 않는다. 운영 중 캘리브레이션 점검(Back-testing)과 리캘리브레이션 판단은 모형 모니터링과 운영을 따른다.

    1.4.2 챌린저 비교¶

    ML 모형은 진공 속에서 평가하지 않는다. 현행 모형(대개 WoE 스코어카드)을 같은 OOT 데이터로 함께 평가해, ML이 더 복잡해진 만큼 얻은 것이 무엇인지 보여 줘야 한다.

    비교 항목 내용
    변별력 차이 같은 OOT에서 KS·AR 차이. 가능하면 부트스트랩으로 차이의 신뢰구간을 함께 제시한다
    Swap Set 분석 같은 승인율에서 한 모형만 승인하는 고객(swap-in)과 한 모형만 거절하는 고객(swap-out)의 건수와 실현 불량률을 비교한다. 변별력 차이가 실제 의사결정에서 어떤 고객 집단의 차이로 나타나는지 보여 준다
    등급 이동 현행 등급과 ML 등급의 교차표. 큰 폭으로 이동한 고객군의 특성과 실현 불량률을 확인한다
    운영 영향 같은 불량률 목표에서 승인율이 얼마나 달라지는가, 또는 같은 승인율에서 불량률이 얼마나 달라지는가

    Cross Matrix로 현행 모형과 ML을 함께 쓰는 하이브리드 구조는 왜 ML인가의 1.5절에서 다룬다.

    1.4.3 하이퍼파라미터·시드 민감도¶

    좋은 성능이 "운 좋은 한 번의 설정"에서 나온 것인지 확인한다.

    • 시드 민감도: 같은 하이퍼파라미터로 시드(행·열 서브샘플링, 데이터 분할)만 바꿔 여러 번 학습해, 검증 KS·AR의 흔들림 폭을 본다. 이 폭보다 작은 성능 차이로 모형을 고르는 것은 의미가 없다
    • 하이퍼파라미터 민감도: 선택한 설정 주변(깊이 ±1, 학습률·트리 수 조정 등)에서 성능이 완만하게 변하는지 본다. 한 지점에서만 성능이 튀는 설정은 검증셋에 과적합된 선택일 가능성이 크다
    • 구조 민감도: 시드를 바꿨을 때 상위 변수 구성과 SHAP 방향이 유지되는지도 함께 본다. 성능은 같아도 설명이 매번 바뀌는 모형은 운영과 설명 의무 대응이 어렵다

    1.4.4 단조성·부호 점검¶

    모형이 학습한 관계가 도메인 상식과 맞는 방향인지 확인한다. "연체 횟수가 늘수록 위험이 커진다", "소득이 높을수록 위험이 작아진다" 같은 관계가 모형 안에서 뒤집혀 있으면, 성능이 좋아도 설명할 수 없다.

    점검 대상 방법
    변수별 방향 SHAP dependence plot, PDP·ICE로 변수 값이 커질 때 예측 위험이 어느 방향으로 움직이는지 확인
    국소적 역전 전체 추세는 맞는데 특정 구간에서만 역전되는지(표본이 적은 극단 구간에서 흔함) 확인
    상관 변수의 부호 분담 상관이 높은 변수 쌍에서 한쪽은 정방향, 다른 쪽은 역방향으로 나뉘어 보이는지 확인 (부록 B. 변수 상관과 모형 해석)
    등급별 불량률 단조성 OOT에서 등급이 나빠질수록 실현 불량률이 단조 증가하는지 확인 (OOT 검증)

    방향이 중요한 변수에는 학습 단계에서 단조 제약(monotone constraint)을 거는 것이 근본 대책이다. XGBoost·LightGBM 등 주요 부스팅 라이브러리가 이 옵션을 제공한다.

    1.4.5 세그먼트별 성능¶

    전체 성능이 좋아도 특정 고객군에서 무너질 수 있다. 주요 세그먼트별로 KS·AR과 캘리브레이션을 따로 본다.

    • 채널: 대면 / 비대면
    • 고객 유형: 신규 / 기존, 신용이력 부족자(thin file) / 이력 충분자
    • 상품·한도 구간: 상품별, 대출금액 구간별
    • 시기: OOT 기간 안에서도 월·분기별

    세그먼트가 작으면 Bad 건수가 적어 KS·AR 자체가 크게 흔들리므로, 건수와 Bad 건수를 반드시 함께 표시하고 필요하면 신뢰구간을 붙인다. 세그먼트 간 성능 차이가 크면 세분화 모형이나 세그먼트 변수 추가를 검토한다.

    1.4.6 SHAP 안정성¶

    ML 모형의 설명(중요 변수, 거절 사유)은 SHAP 등으로 만들어진다. 설명이 시점에 따라 크게 바뀌면 설명 의무 대응과 모형 신뢰에 문제가 생긴다.

    점검 항목 방법
    중요도 순위 안정성 개발 데이터와 OOT(또는 운영 월별 데이터)에서 \(\text{mean}(\|\phi_j\|)\) 순위를 구하고, 순위 상관(Spearman)과 상위 k개 변수의 겹침 비율을 본다
    방향 안정성 변수별 SHAP dependence의 방향이 시점 간에 유지되는가
    기여 분포 변화 변수별 SHAP 값 분포를 PSI처럼 시점 간 비교한다. 입력 분포 변화(CSI)와 함께 보면 "입력이 바뀌어서"인지 "같은 입력에 대한 기여가 바뀌어서"인지 구분할 수 있다
    기여 집중도 소수 변수에 기여가 과도하게 몰리면, 그 변수의 데이터 품질 문제나 분포 변화에 모형 전체가 취약해진다

    모형의 파라미터는 운영 중 고정되어 있으므로, SHAP 값이 변하는 것은 입력 데이터의 분포가 변했기 때문이다. 이 점은 스코어카드도 같다. 스코어카드의 β는 고정이지만 변수 구간 분포가 바뀌면 배점 분포가 바뀌며, 이것을 CSI로 감시한다. SHAP 안정성 점검은 ML 모형판 CSI·배점 분포 점검이라고 보면 된다. 순위 상관이 몇 이상이어야 한다는 공인 기준은 없으므로, 기준값은 개발 단계의 시드 민감도(1.4.3)에서 관찰한 자연 변동 폭을 바탕으로 내부적으로 정한다.

    1.4.7 공정성 점검¶

    성별·연령 등 민감 정보를 변수에서 제외해도, 그와 상관된 대리 변수(proxy)를 통해 간접적인 차별 효과가 생길 수 있다. ML 모형은 변수 조합을 자동으로 학습하므로 이런 대리 효과를 사람이 미리 알아차리기 어렵다.

    점검 항목 방법
    결과 격차 민감 집단별 승인율, 평균 점수, 등급 분포를 비교한다
    집단별 캘리브레이션 같은 점수 구간 안에서 집단별 실현 불량률이 같은지 본다. 같은 점수인데 한 집단의 실현 불량률이 체계적으로 낮다면, 그 집단이 점수상 불리하게 평가되고 있다는 신호다
    집단별 변별력 집단별 KS·AR을 비교한다
    대리 변수 탐지 민감 속성을 타겟으로 모형 변수들이 그것을 얼마나 예측하는지 확인하고, 기여가 큰 변수를 검토한다

    민감 변수를 모형에 넣지 않았다면 그 변수의 SHAP 값은 0이므로, SHAP만으로는 공정성을 판단할 수 없다. 민감 속성은 모형 밖에서 점검용으로만 결합해 위 지표를 계산한다. 법적 배경은 규제 프레임워크에서 다룬다.

    1.5 모니터링¶

    PSI/CSI를 통한 분포 안정성 모니터링, 변별력 추이 추적, Back-testing, 리캘리브레이션 vs 재개발 판단, 거버넌스 체계는 전통 스코어카드와 ML 모형에 공통으로 적용된다. 상세 내용은 모형 모니터링과 운영을 따른다. ML 모형에서 달라지는 점만 정리하면 다음과 같다.

    항목 전통 스코어카드 ML (트리 앙상블)
    입력 분포 감시 변수 10~20개의 CSI 변수 수십~수백 개의 CSI → 자동화 필수. 기여도가 큰 변수부터 우선순위를 둔다
    기여 구조 감시 구간 분포 변화에 따른 배점 분포 변화(CSI로 감시) SHAP 중요도 순위·방향·분포 감시 (1.4.6)
    캘리브레이션 감시 등급별 예측 PD vs 실현 불량률 동일. ML은 확률 왜곡이 생기기 쉬워 보정 함수의 유효성까지 함께 점검
    점수 분포 구간 점수 구간(또는 등급) 기준 PSI 동일. 거의 연속인 점수를 구간화할 때 개발 시점의 구간 경계를 고정해 쓴다
    재현성·운영 환경 점수표 계산식 고정 모형 파일, 라이브러리 버전, 전처리 코드, 실행 환경 고정(pinning)과 변경 이력 관리
