# 규제 프레임워크

---

## 5.1 모형 리스크 관리의 필요성

신용평가모형은 여신 심사, 충당금 적립, 규제자본 산출 등 **금융 의사결정의 핵심 인프라**다. 모형이 잘못되면 부실 여신이 늘어나고, 충당금이 과소 적립되며, 규제자본이 부족해진다. 그래서 주요국 감독당국은 모형의 개발·검증·운영 전 과정에 걸친 **체계적인 리스크 관리**를 요구한다.

---

## 5.2 미국 모형리스크 관리 지침 — SR 11-7에서 SR 26-2로

미국 연방준비제도(Fed)와 통화감독청(OCC)이 2011년 4월 공동으로 낸 **SR 11-7 "Guidance on Model Risk Management"** 는 오랫동안 금융 모형리스크 관리의 대표적 참고 문서였고, 국내 금융회사도 벤치마크로 많이 참고했다. 이 지침은 **2026년 4월 17일 SR 26-2로 대체**되었다. SR 26-2는 Fed·FDIC·OCC가 공동으로 낸 개정 지침이다.

| 구분 | SR 11-7 (2011) | SR 26-2 (2026) |
|------|---------------|----------------|
| **발행** | Fed, OCC | Fed, FDIC, OCC |
| **접근 방식** | 모든 모형에 폭넓게 적용 | **리스크 기반(risk-based)** — 모형의 중요도(materiality: 노출 규모 + 용도)와 내재 리스크에 비례해 관리 강도 조절 |
| **주 적용 대상** | 은행 조직 전반 | 총자산 300억 달러 초과 은행 조직에 가장 관련 (작은 조직도 모형 리스크가 크면 해당) |
| **성격** | 감독 지침 | 집행 가능한 기준이나 규범적 요구사항이 아니라고 명시 |
| **AI 모형** | 별도 언급 없음 | 전통 통계·정량 모형과 **비생성형 AI 모형**에 적용, 생성형·에이전트형 AI는 범위 밖 |

### 핵심 요소 (두 지침에 공통)

| 요소 | 내용 |
|------|------|
| **개념적 건전성 (Conceptual Soundness)** | 모형 설계(주요 선택, 가정, 정성 판단, 데이터 선택), 구축, 개발 단계 검증(developmental evidence)의 타당성. SR 26-2는 해석 가능성 지표나 다른 모형과의 비교(benchmarking)도 평가 수단으로 든다 |
| **지속 모니터링 (Ongoing Monitoring)** | 상품·고객·데이터·시장 여건 변화 속에서 모형이 기대대로 작동하는지 계속 평가 |
| **결과 분석 (Outcomes Analysis)** | 모형 출력과 실제 결과의 비교 — Back-testing, 이상치 분석 등 |
| **효과적 도전 (Effective Challenge)** | 적절한 전문성·독립성·조직 내 영향력을 갖춘 사람이 모형을 비판적으로 검토하고 필요한 변경을 이끌어 내는 것 |
| **거버넌스 (Governance)** | 정책·통제, 역할과 책임, 모형 목록·변경 관리, 내부감사의 역할 |

SR 26-2는 모형 테스트의 예로 **out-of-sample·out-of-time 테스트**를 명시한다([OOT 검증](oot-validation.md)).

### 전통 스코어카드에서의 적용

전통 스코어카드는 이 지침의 관점에서 **상대적으로 검증이 쉬운** 모형이다.

- **변수 효과가 투명:** WoE 변환 → 로지스틱 회귀 → 점수표로, 각 변수의 기여가 점수로 직접 표현됨
- **개념적 건전성 설명이 직관적:** "연체 횟수가 많으면 점수가 낮아진다"를 점수표로 보여줄 수 있음
- **결과 분석 용이:** 등급별 예측 PD와 실현 부도율 비교가 명확
- **거절 사유 설명:** 항목별 최고 배점 대비 잃은 점수가 큰 항목을 거절·불리한 결정의 사유로 제시할 수 있다(감점의 기준점과 동점 처리 규칙은 미리 정해 둔다). 국내에서도 개인은 자동화평가 결과에 대해 설명과 정보 정정·재산출을 요구할 수 있다(신용정보법 제36조의2).

!!! info "ML 모형과의 대비"
    ML 모형(XGBoost, Random Forest 등)은 "개념적 건전성"과 "효과적 도전"에서 추가적인 노력이 필요하다. 변수 간 비선형 상호작용이 있고, SHAP 등 사후 해석에 의존하는 경우가 많기 때문이다. ML 모형의 규제 대응은 [ML 섹션 — 규제 프레임워크](../../ml/part5_validation/regulatory.md)에서 다룬다.

## 5.3 Basel IRB — 내부등급법 모형 요건

Basel II/III 내부등급법(Internal Ratings-Based Approach, IRB)을 적용하는 은행은 자체 신용등급 모형으로 **규제자본**을 산출한다. 그래서 모형 품질이 은행의 자본 적정성에 직접 영향을 미치고, 감독당국은 엄격한 요건을 둔다. 아래는 이 가이드북에서 다룬 내용과 직접 관련된 Basel II(BCBS 128) 요건이다.

| 요건 | 내용 | BCBS 128 문단 |
|------|------|------|
| **등급 구조** | 기업·국가·은행 익스포저는 부도 전 차주 등급 최소 7개 + 부도 등급 1개 | 404 |
| **모형 사용** | 평점 모형을 등급 부여의 기초로 쓸 수 있으나, 모형 밖의 중요 정보도 인적 판단으로 반영 | 417 |
| **통계적 검증** | 통계 모형은 **out-of-time·out-of-sample 성능 검정을 포함한** 엄격한 통계적 검증 절차를 갖출 것 | 420 |
| **Override 관리** | Override를 식별하고 그 성과를 별도로 추적 | 428 |
| **연간 검토** | 내부감사 등 독립 기능이 등급 체계를 적어도 연 1회 검토 | 443 |
| **관측 기간** | PD 추정 데이터는 기업(적어도 한 원천)·소매 모두 최소 5년 | 463, 466 |
| **결과 분석** | 등급별 실현 부도율과 추정 PD를 정기 비교하고, 분석을 적어도 연 1회 갱신 | 501 |

<div class="source-ref">출처: <a href="https://www.bis.org/publications/200606-standards-basel-ii-international-convergence-capital-measurement-and-capital-standards-revised-framework.pdf" target="_blank">BCBS, International Convergence of Capital Measurement and Capital Standards — Comprehensive Version (2006.6)</a></div>

### Calibration 실패의 대가

Back-testing에서 예측 PD가 실현 부도율을 체계적으로 **과소 추정**하는 것이 확인되면, 감독당국은 보수적 조정이나 추가 자본을 요구할 수 있다. 이는 은행의 수익성에 직접 영향을 주므로, Calibration 모니터링은 통계 검증을 넘어 **경영 이슈**다([모니터링과 운영](monitoring-and-operations.md)).

## 5.4 국내 규제 환경

### 개인신용평가체계 검증

국내 CB사의 개인·개인사업자 신용평가 모형은 신용정보법 제26조의3에 따른 **개인신용평가체계 검증위원회**의 정기 검증을 받고, 공개용 결과 보고서가 나온다. 보고서에는 회사별 개발 시점 대비 검증 시점의 AR·KS·PSI가 담긴다([성능 벤치마크](performance-ks-ar-gini.md), [모니터링 참고자료](monitoring-and-operations.md)).

### 금융회사 내부 모형 운영에서 흔히 요구되는 사항

은행 등 금융회사는 감독당국의 검사·지도와 내부 규정에 따라 신용평가모형을 관리한다. 구체적인 요건은 업권과 모형 용도(내부등급법 적용 여부 등)에 따라 다르지만, 실무에서 공통적으로 갖추는 항목은 다음과 같다.

| 항목 | 내용 |
|------|------|
| **정기 검증** | 적어도 연 1회 모형 성능 검증 (내부등급법 은행은 Basel 요건) |
| **안정성 모니터링** | PSI 등 안정성 지표의 정기 모니터링 |
| **모형 변경 관리** | 중요한 변경·폐기 시 내부 승인, 필요 시 감독당국 보고 |
| **기록 보존** | 개발·검증 결과와 조치 이력을 내부 규정에 따라 보존 |
| **개발 기록** | 변수 선정 근거, 모형 구조, 검증 결과를 포함한 개발 보고서 |

구체적인 보존 기간이나 보고 절차는 해당 금융회사의 업권별 감독규정과 내부 규정을 확인한다.

### 금융분야 AI 가이드라인

금융위원회는 2021년 7월 **금융분야 AI 가이드라인**을 발표했다(4대 핵심가치: 책임성, 데이터 정확성·안전성, 투명성·공정성, 소비자 권리 보장). 이후 기존 가이드라인을 통합·개정해 2025년 12월 개정안을 내고, 2026년 6월 최종안을 발표했다(2026년 6월 22일 시행). 개정 가이드라인은 7대 원칙을 제시한다.

1. **거버넌스** — AI 시스템의 책임 소재를 명확히
2. **합법성** — 관련 법규 준수
3. **보조수단성** — 인간의 판단을 AI가 보완
4. **신뢰성** — 정확성, 안정성, 재현성 확보
5. **금융안정성** — 시스템 리스크 방지
6. **신의성실** — 소비자 이익 보호
7. **보안성** — 데이터 보호, 사이버 보안

최종안 발표 때 금융감독원의 **금융분야 AI 위험관리 프레임워크**도 함께 배포되었다.

!!! tip "전통 스코어카드와 AI 가이드라인"
    전통 로지스틱 회귀 스코어카드가 이 가이드라인의 "AI"에 해당하는지는 가이드라인의 정의와 각 금융회사의 판단에 따라 달라질 수 있다. 다만 **ML 챌린저 모형**을 병행 운용하거나 ML 기반 모형으로 전환하면 적용 대상이 된다고 보고 준비하는 것이 안전하다. 어느 쪽이든 위 7대 원칙(설명 가능성, 재현성, 책임 소재 등)은 전통 스코어카드 운영 원칙과 크게 다르지 않다. ML 모형의 규제 대응은 [ML 섹션 — 규제 프레임워크](../../ml/part5_validation/regulatory.md)에서 상세히 다룬다.

## 5.5 해외 규제 동향

### EU AI Act — 신용평가 AI는 "고위험"

EU AI Act는 자연인의 신용도 평가·신용점수 산출에 쓰이는 AI 시스템을 **고위험(High-risk)** 으로 분류한다(사기 탐지 목적은 제외). 고위험 시스템에는 위험관리, 데이터 거버넌스, 문서화, 투명성, 인적 감독 등이 요구된다.

### EBA — IRB 모형의 머신러닝 활용 후속 보고서 (2023)

유럽은행감독청(EBA)은 IRB 모형에 ML을 쓰는 은행의 실태를 조사했다. 설명 가능성 확보 수단으로는 **Shapley 값(응답 기관의 40%)**, 그래프 도구(20%), 보고·문서화 강화(28%), 민감도 분석(8%)이 쓰였다.

### ECB — 내부모형 가이드 (2025 개정)

ECB의 내부모형 가이드는 내부모형에서의 **머신러닝 기법 활용**을 별도 절로 다루며, 은행이 모형 결과에 대한 전체·개별 수준의 기여를 평가할 수 있는 **설명 가능성 기법과 도구들**을 갖출 것을 기대한다. 특정 기법을 지정하지는 않는다.

<div class="source-ref">출처: <a href="https://www.eba.europa.eu/sites/default/files/document_library/Publications/Reports/2023/1061483/Follow-up%20report%20on%20machine%20learning%20for%20IRB%20models.pdf" target="_blank">EBA, Follow-up report on machine learning for IRB models (EBA/REP/2023/28)</a>, <a href="https://www.bankingsupervision.europa.eu/ecb/pub/pdf/ssm.supervisory_guide202507.en.pdf" target="_blank">ECB Guide to internal models (2025.7)</a></div>

!!! info "해외 규제의 시사점"
    미국(SR 26-2)과 유럽(EU AI Act, EBA, ECB)의 방향은 같다: **설명할 수 없는 모형은 점점 운영하기 어려워진다.** 전통 스코어카드는 이 요건을 구조적으로 충족하며, 규제 환경에서 여전히 표준적인 모형으로 쓰이는 이유 중 하나다.

## 5.6 모형 문서화 — 무엇을 남겨야 하는가

규제 검증에서 자주 지적되는 사항 중 하나가 **문서화 미비**다. 모형 개발 보고서에는 최소한 다음 항목이 들어가야 한다.

| 구분 | 필수 항목 |
|------|-----------|
| **모집단 설계** | Target 정의(Good/Bad), 성과 기간, 제외 기준, 표본 설계 근거 |
| **변수 선정** | 초기 변수풀, Fine/Coarse Classing 과정, WoE/IV 평가, 단변량·다변량 검정 결과 |
| **모형 구조** | 최종 변수, 회귀계수, 스코어카드 변환 파라미터 (Anchor, 기준 Odds, PDO) |
| **성능 평가** | KS, AR — 개발/OOS/OOT 대비표 |
| **안정성 검증** | PSI, CSI, 등급별 부도율 단조성 |
| **한계 및 가정** | 모형이 잘 작동하지 않는 세그먼트, 데이터 제약, 가정의 한계 |
| **변경 이력** | 기존 모형 대비 변경 사항, 변경 사유, 성능 비교 |

!!! warning "실무 팁 — 문서화는 개발과 동시에"
    모형 개발이 끝난 뒤 문서를 쓰면 변수 선정 과정의 세부 의사결정 근거가 사라지기 쉽다. **개발 단계마다 의사결정 기록을 남기고**, 최종 보고서는 이를 정리하는 방식이 효율적이다.
