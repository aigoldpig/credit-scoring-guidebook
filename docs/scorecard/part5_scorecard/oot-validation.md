모형 성능 평가에서 KS·AR이 아무리 높아도, **개발 데이터에서만 잘 작동하는 모형은 실전에서 쓸 수 없다.** OOT 검증은 모형이 **미래 데이터에서도 유효한지** 확인하는 가장 중요한 관문이다.

---

## 3.1 왜 OOT가 필요한가

### 개발 표본의 한계

개발 표본(Training)에서 산출한 KS·AR은 모형이 이미 "본 적 있는" 데이터에 대한 성능이다. 이 수치가 높다고 해서 미래에도 같은 성능이 보장되지 않는다.

| 검증 유형 | 데이터 원천 | 확인 사항 |
|-----------|-----------|-----------|
| **In-Sample (Training)** | 모형 학습에 사용한 데이터 | 모형이 데이터를 잘 학습했는가 (과적합 가능) |
| **OOS (Hold-out)** | 같은 기간 내 무작위 분리 | 과적합 여부 1차 점검 |
| **OOT (Out-of-Time)** | 개발 기간 **이후** 시점의 데이터 | 시간 변화에 대한 강건성 (실전 유효성) |

!!! warning "OOS만으로는 부족한 이유"
    OOS는 개발 표본과 **같은 시점**의 데이터를 무작위로 나눈 것이다. 같은 경제 환경, 같은 심사 정책, 같은 포트폴리오 구성을 공유하므로 **시간 변화에 따른 열화를 감지하지 못한다.** "이 모형이 내일도 통하는가"에 가장 가깝게 답하는 것은 OOT다.

!!! info "규제 문서에서의 근거"
    Basel II는 통계 모형을 등급 부여에 쓰는 은행에 **"out-of-time 및 out-of-sample 성능 검정을 포함한 엄격한 통계적 검증 절차"** 를 갖추도록 요구한다(BCBS 128 문단 420). 또 등급별 실현 부도율과 추정 PD를 정기적으로 비교하고 그 분석을 적어도 연 1회 갱신하도록 요구한다(문단 501).

    <div class="source-ref">출처: <a href="https://www.bis.org/publications/200606-standards-basel-ii-international-convergence-capital-measurement-and-capital-standards-revised-framework.pdf" target="_blank">BCBS, Basel II Comprehensive Version (2006), 문단 420·501</a></div>

### 개발·검증 표본 설계

> **관측 윈도우** (변수 산출 기간) → **성과 윈도우** (불량 판정 기간)

| 구분 | 관측 시점 (예시) | 용도 |
|------|------------|------|
| **개발 표본** | 2021.01 ~ 2022.06 | 모형 학습 |
| **OOS** | 같은 기간에서 20~30% 무작위 분리 | 과적합 점검 |
| **OOT** | 2022.07 ~ 2023.06 | 시간 안정성 검증 |

이 페이지의 OOS는 같은 기간 안에서 떼어 둔 Hold-out을 가리킨다(ML 파트는 개발에 쓰지 않은 표본 전체를 OOS로 부른다). OOT라고 부를 수 있는 것은 개발 기간 뒤 시점 중 성과 기간이 끝난 표본을 개발 모형 그대로 채점한 결과뿐이다. 학습 기간보다 과거 시점에 적용한 결과는 "안정성 진단"으로, 성과가 아직 끝나지 않은 최근 시점은 "분포 점검"(PSI)으로 구분해 적는다.

!!! tip "OOT 기간 설정 실무"
    - OOT 기간은 최소 **6개월~1년** 이상이 권장된다.
    - **성과 윈도우(Performance Window)** 가 12개월이면, 관측 시점에서 12개월이 지나야 불량 여부가 확정된다. 위 예시의 OOT 표본은 2024년 6월이 지나야 모두 확정된다. 그래서 OOT 관측 시점은 현재보다 최소 성과 윈도우만큼 앞서야 한다.
    - 경기 변동을 포착하려면 OOT 기간이 개발 기간과 **다른 경기 국면**을 포함하는 것이 이상적이다.

!!! warning "같은 차주가 여러 시점에 반복 관측되는 자료"
    여러 기준시점의 스냅샷을 합친 자료를 무작위로 나누면, 한 차주의 서로 다른 시점이 학습과 검증에 나뉘어 들어가 검증 성능이 실제보다 좋게 나온다. 차주 단위로 묶어 나누거나, 최신 시점을 먼저 OOT로 떼어 둔 뒤 나머지에서 학습·검증 표본을 나눈다.

## 3.2 OOT에서 확인할 사항

### 변별력 안정성 — OOT 허용폭 (기준값 정본)

이 표가 가이드북 전체의 **OOT 허용폭 정본**이다. ML 모형 검증 등 다른 페이지는 이 표를 참조한다.

| 지표 | 양호 | 주의 (원인 분석) | 재검토 | 판정 예시 |
|------|------|--------------|------|-----------|
| **KS 하락폭** (개발 KS − OOT KS, %p) | ≤ 5 | 5 ~ 10 | > 10 | 개발 38.2 → OOT 34.1 (−4.1%p, 양호) |
| **AR 하락폭** (개발 AR − OOT AR) | ≤ 0.05 | 0.05 ~ 0.10 | > 0.10 | 개발 0.54 → OOT 0.50 (−0.04, 양호) |
| **PSI** (개발 vs OOT 점수 분포) | < 0.10 | 0.10 ~ 0.25 | > 0.25 | 0.06 (양호) |

- KS 하락폭은 **절대 차이(%p)** 다. "KS가 10% 하락"(상대 비율)과 혼동하지 않는다.
- 개발 시점 성능 자체의 수준(벤치마크)은 [성능 평가 2.4절](performance-ks-ar-gini.md)에서 판단한다.
- AUC는 AR과 1:1로 환산되므로(AR = 2·AUC − 1) 별도 기준을 두지 않는다. AR 0.05 하락은 AUC 0.025 하락과 같다.

!!! warning "허용폭은 실무 경험칙이다"
    위 기준은 업계에서 흔히 쓰는 경험칙이지, 규제가 정한 일률적 수치는 아니다. 모형 용도(심사 자동화 vs 참고용), 포트폴리오 특성(소매 vs 기업), 불량 건수에 따라 허용 범위가 달라질 수 있다. 특히 불량 건수가 적으면 OOT KS·AR 자체의 표본 오차가 커서, 몇 %p의 하락은 우연일 수 있다(부트스트랩 신뢰구간으로 확인). 중요한 것은 **하락의 크기와 원인을 함께 보는 것**이다. 같은 차주가 여러 관찰 시점에 반복되는 자료라면 관측행이 독립이 아니어서 행 단위 신뢰구간이 실제보다 좁게 나오므로, 차주 단위로 재표집한다. 허용폭과 판정 기준은 결과를 보기 전에 정해 두고, 결과를 본 뒤 새 기준을 만들어 합격을 주장하지 않는다.

### 등급별 부도율 단조성 (Monotonicity)

OOT에서도 **등급이 나쁠수록 부도율이 높아지는** 단조 관계가 유지되어야 한다. 개발 표본에서 단조였더라도 OOT에서 역전이 생기면, 해당 구간의 변수-위험 관계가 바뀌었을 가능성이 있다.

| 등급 | 개발 부도율 | OOT 부도율 | 판정 |
|------|-----------|-----------|------|
| 1 (최우량) | 0.3% | 0.4% | 정상 |
| 2 | 0.8% | 1.0% | 정상 |
| 3 | 1.5% | 1.8% | 정상 |
| 4 | 3.2% | 3.5% | 정상 |
| **5** | **5.5%** | **3.3%** | **역전 — 4등급(3.5%)보다 낮음, 점검 필요** |
| 6 (최불량) | 10.2% | 12.1% | 정상 |

!!! tip "단조성 이상 시 조치"
    ① 해당 등급의 관측 수·불량 수가 극소수인지 확인 (소표본 변동 가능성)
    ② 해당 등급에 많이 속한 구간의 **변수-위험 관계가 바뀌었는지** 확인: OOT 표본에서 변수별 구간 불량률·WoE를 다시 계산해 개발 값과 비교하거나, 개발 WoE를 OOT 표본에 적용해 단변량 로지스틱 회귀를 다시 적합한다(정상이면 계수가 −1 근처 — [증명](../part3_variable_selection/univariate_lr/beta-woe-proof.md)). CSI는 구성비 이동만 보므로 이 점검에는 쓸 수 없다.
    ③ 역전이 통계적으로 유의하고 지속되면 해당 등급 구간 합병 또는 Coarse Classing 재검토

### 점수 분포 안정성

OOT 표본의 점수 분포가 개발 표본과 비슷한지 PSI로 확인한다. 판정 기준은 위 허용폭 표와 같고, 산출 방법은 [성능 평가](performance-ks-ar-gini.md)의 PSI 절에서 다룬다.

## 3.3 OOT 성능이 크게 떨어졌을 때

OOT에서 성능이 급락했다면, **모형의 문제인지 환경의 문제인지** 구분하는 것이 첫 번째 단계다.

### 원인 진단 체크리스트

| 점검 항목 | 모형 문제 시그널 | 환경 변화 시그널 |
|-----------|----------------|----------------|
| **OOS 성능** | OOS도 개발 대비 크게 하락 → 과적합 | OOS는 양호, OOT만 하락 |
| **PSI** | 낮음 (분포가 같은데 성능만 하락) | 높음 (모집단 구성 자체가 변동) |
| **CSI** | 특정 변수만 급등 → 그 변수의 데이터·정의 이상 | 다수 변수가 함께 상승 → 경기·정책 변화 |
| **변수별 WoE 재계산** | — | 분포는 같은데 구간별 불량률이 변함 → **개념 드리프트**(변수와 위험의 관계 변화) |
| **데이터 누수** | 특정 변수를 빼면 개발 성능이 크게 떨어지고 OOT와 비슷해짐 | 변수를 빼도 변화 없음 |

PSI가 낮은데 성능이 떨어지면 "모형 문제"로 단정하기 쉽지만, 경기 변화로 **같은 점수대의 부도 행태가 바뀐 경우**(개념 드리프트)도 같은 모습을 보인다. 변수별 구간 불량률을 개발 시점과 비교해 구분한다.

!!! danger "Target Leakage 점검"
    Leakage(불량 판정 이후에야 관측 가능한 정보가 변수에 섞임)는 **개발 표본 성능을 부풀린다.** OOT에서 그 정보가 같은 방식으로 들어오지 않으면 성능이 크게 떨어지고, 같은 방식으로 들어오면 OOT도 비현실적으로 높게 나온다.

    - **개발·OOT 모두 비현실적으로 높은 경우:** 연체일수·채권회수 단계 등 사후 정보가 변수에 포함됐는지, 관측 시점 기준 데이터 추출이 맞는지 확인
    - **개발만 높고 OOT에서 급락하는 경우:** 개발 기간에만 존재했던 사후 정보(예: 데이터 적재 시점 차이)가 있었는지 확인

### 대응 방향

```
OOT 성능 급락
    │
    ├─ 모집단 변화 (PSI 높음)
    │   ├─ 일시적 (경기 충격 등) → 모니터링 지속, 다음 OOT 재확인
    │   └─ 구조적 (채널·상품·정책 변경) → 리캘리브레이션 또는 재개발
    │
    ├─ 관계 변화 (PSI 낮음, 구간별 불량률 변화) → 해당 변수 Classing 재검토 또는 재개발
    │
    ├─ 과적합 (OOS도 하락)
    │   └─ 변수 축소, Bin 수 축소, 표본 증량 검토
    │
    └─ 데이터 누수 (Leakage)
        └─ 해당 변수 제거 후 재개발
```

## 3.4 실무 보고 — OOT 검증 보고서 구성

OOT 검증 결과는 모형 승인의 핵심 근거로, 내부 검증 부서와 감독당국에 제출하는 **공식 문서**다.

### 보고서 필수 항목

| 항목 | 내용 |
|------|------|
| **개발·OOT 표본 정의** | 기간, 건수, 불량률, 제외 기준 |
| **변별력 비교** | KS, AR — 개발 vs OOS vs OOT 대비표 |
| **PSI** | 점수 분포 이동량 |
| **등급별 부도율** | 개발 vs OOT 대비, 단조성 확인 |
| **변수 안정성** | 주요 변수 CSI, 구간별 불량률 변화 |
| **종합 판정** | 모형 승인 / 조건부 승인 / 반려 |

!!! example "실무 참고 — OOT 검증 관행"
    신용평가모형 개발 시 최소 1개 이상의 OOT 기간을 설정하여 검증하는 것이 일반적이다. 개인 CSS는 개발 기간 2~3년, OOT 기간 1년 정도가 흔하며, 기업 CSS는 불량 건수 확보를 위해 개발 기간을 더 길게 잡는 경우가 많다. 공개된 개인신용평가체계 검증위원회 보고서도 개발 시점과 검증 시점의 AR·KS·PSI를 나란히 비교하는 형식을 쓴다([벤치마크 표](performance-ks-ar-gini.md)).

!!! info "다음 단계"
    OOT 검증을 통과한 모형은 배포 후 [모니터링과 운영](monitoring-and-operations.md) 체계에 편입된다. PSI·CSI로 분포 안정성을, KS·AR 추이로 변별력을, Back-testing으로 예측 정확성을 지속 감시한다.
