# 스코어와 의사결정

## 6.1 확률 → 평점 → 등급

모형이 적합되면 각 차주에 대해 **불량 확률 \(\hat{p}\)**가 산출된다. 이 확률을 실무에서 활용하기 위해 다음과 같은 변환 과정을 거친다.

> **불량 확률 \(\hat{p}\)** (모형 직접 산출값, 예: 0.012) → **신용 점수(Score)** (PDO 변환, 예: 700점) → **신용 등급(Grade)** (구간화, 예: 3등급) → **비즈니스 의사결정** (승인·한도·금리)

**PDO(Points to Double the Odds)** 변환은 "Good Odds(불량 대비 정상)가 2배가 될 때 점수가 일정 간격(예: 20점)만큼 증가한다"는 규칙으로 확률을 점수로 환산하는 방법이다. 예를 들어 PDO=20이면 Good Odds가 10:1인 고객과 20:1인 고객의 점수 차이는 정확히 20점이다. 점수는 \(\ln(\text{Good Odds})\)의 선형 변환이므로 **점수 차이가 log-odds 차이에 비례**하고, 점수가 높을수록 우량하다는 직관적 해석이 가능해진다. 모형은 Bad Odds로 적합하므로, 같은 계수로 \(\ln(\text{Good Odds}) = -\,\text{logit}_{\text{Bad}}\)를 계산해 부호를 뒤집는다. PDO 변환의 수식 유도와 스코어카드 구성 방법은 **[스코어카드 변환](../part5_scorecard/scorecard-and-rating.md)**에서 상세히 다룬다.

**등급화(Grading)**는 점수를 일정 구간으로 나누어 등급을 부여하는 과정이며, 등급별 불량률 서열화, 구성비 적정성 등을 고려하여 설계한다. 등급마다 붙이는 PD 숫자(등급별 PD)를 어떻게 정하는지는 [여신 프로세스 — PD 용어 정리](../../lending_process/terms/pd.md)에서 다룬다.

## 6.2 모형 성능은 어떻게 판단하는가

개발된 모형이 실무에서 쓸 만한지를 판단하는 기준은 크게 세 가지다.

| 관점 | 질문 | 주요 지표 |
|------|------|------|
| **변별력** (Discrimination) | Good과 Bad를 얼마나 잘 구분하는가? | KS(%p), AR(소수, = Gini) |
| **안정성** (Stability) | 시점이 바뀌어도 점수 분포가 안정적인가? | PSI |
| **정확성** (Calibration) | 등급별 예측 PD가 실현 부도율과 맞는가? | 등급별 예측 vs 실현 부도율 비교(Back-testing) |

지표별 판단 기준값(개인/기업, 개발/OOT)은 기관·상품·시장 상황에 따라 다르며, 본 가이드북은 이를 **[성능 평가 — 실무 성능 기준](../part5_scorecard/performance-ks-ar-gini.md)** 한 곳에 모아 두었다. BS모형은 내부 거래 이력이라는 강력한 정보를 쓰므로 일반적으로 AS모형보다 변별력이 높게 나온다. 따라서 AS모형의 기준을 BS모형에 그대로 적용하지 않는다.

### 변별력 지표 미리보기

변별력을 측정하는 대표적 통계량을 간단히 소개한다. 각 지표의 수식, 차트, 해석법은 **[성능 평가 (KS·AR·Gini)](../part5_scorecard/performance-ks-ar-gini.md)**에서 상세히 다룬다.

| 지표 | 한 줄 정의 | 직관적 해석 |
|------|-----------|------------|
| **KS** (Kolmogorov-Smirnov) | Good/Bad 누적분포 간 **최대 거리** (%p) | "모형이 불량자를 저점수 구간에 얼마나 집중시키는가"의 최대 분리 정도 |
| **AR** (Accuracy Ratio) / **Gini** | CAP 곡선 기반 **전체 면적 비율** (0~1) | 저점수(고위험)부터 선발할 때 Bad를 얼마나 빨리 포착하는가 |
| (참고) **AUC** | ROC 곡선 아래 면적 | 임의로 고른 Good의 점수가 Bad보다 높을 확률. AR = 2×AUC−1 |

업권에 따라 1차로 보는 지표가 다른 관행(소매 KS, 기업 AR)과 그 이유는 [분류가 아닌 서열화](ranking-not-classification.md)와 [성능 평가](../part5_scorecard/performance-ks-ar-gini.md)에서 다룬다.

!!! note "변별력과 안정성은 함께 봐야 한다"
    개발 표본의 KS·AR을 최대한 끌어올리는 방향으로만 모형을 다듬으면 안정성이 나빠지기 쉽다. 구간을 지나치게 잘게 나누거나, 개발 기간에만 유난히 잘 맞는 변수(정책 변경·일시적 경기 상황의 영향을 받은 변수)에 의존하거나, 변수 수를 과도하게 늘리면 개발 표본에 **과적합**되어 OOT 표본에서 변별력이 떨어지고 점수 분포(PSI)도 흔들린다.
    즉 "변별력이 높으면 안정성이 낮다"는 일반 법칙이 있는 것이 아니라, **개발 표본에 맞춘 복잡도**가 둘 사이의 긴장을 만든다. 그래서 실무에서는 개발 표본 성능뿐 아니라 OOT 표본의 KS·AR과 PSI를 함께 보고 모형을 확정한다([OOT 검증](../part5_scorecard/oot-validation.md)).

## 6.3 비즈니스 활용: 승인·한도·금리

모형이 산출한 점수(또는 등급)는 금융기관의 **여신 의사결정** 전반에 활용된다.

| 의사결정 | 활용 방식 | 예시 |
|------|------|------|
| **승인 / 거절** | Cut-off Score를 설정하여 기준 점수 이상이면 승인, 미만이면 거절 | 600점 미만 → 거절 / 600점 이상 → 승인 |
| **한도 설정** | 점수(등급)에 따라 대출 한도를 차등 부여 | 1~3등급: 최대 5,000만원 / 4~6등급: 최대 2,000만원 |
| **금리 차등** (Risk-Based Pricing) | 리스크 수준에 따라 적용 금리를 차등화 | 1등급: 기준금리 + 1% / 5등급: 기준금리 + 4% |
| **기존 고객 관리** | BS모형 점수 변동을 모니터링하여 한도 상·하향, 조기 경보 | 전월 대비 2등급 이상 하락 시 한도 재심사 트리거 |

여신 프로세스 전체에서 각 단계가 점수·등급·PD를 어떻게 쓰는지는 [여신 프로세스와 신용평가모형의 위치](../../lending_process/index.md)에서 정리한다.

!!! tip "Cut-off 최적화"
    Cut-off Score를 높이면 승인율이 낮아지고 불량률도 낮아진다(보수적). 반대로 Cut-off를 낮추면 승인율이 높아지고 수익 기회가 늘지만 불량률도 올라간다.

    최적 Cut-off는 다음 방법으로 결정한다.

    - **손익 분석(Profit/Loss Analysis):** 각 점수 구간에서 승인 시 기대 수익(이자 수익 − 예상 손실 − 비용)을 계산하여, 기대 수익이 양(+)인 마지막 구간을 Cut-off로 설정
    - **승인율-불량률 트레이드오프 차트:** X축을 Cut-off Score, Y축을 승인율(좌)과 불량률(우)로 그려 경영진이 수용 가능한 불량률 수준에서 Cut-off 결정
    - **규제 제약 반영:** DSR 규제, 가계대출 총량 관리 등 외부 요인으로 인해 승인 가능 규모가 제한되는 경우 이를 Cut-off에 반영

    최종 Cut-off는 리스크 부서와 사업 부서 간 협의를 통해 확정된다.

## 6.4 사전 필터링(Pre-Screen)과 사후 필터링(Post-Screen)

CSS 모형 점수만으로 여신 의사결정이 완결되는 것은 아니다. 모형 평가 **이전**과 **이후**에 별도의 필터링 단계가 존재하며, 이를 통해 모형이 포착하지 못하는 리스크를 보완한다.

### 모형과 필터링룰의 역할 분담

이 관계를 직관적으로 이해하기 위해, 업계에서 종종 쓰이는 비유를 빌려 보자.[^filter-analogy]

- **CSS 모형** = **칼로 크게 도려내기.** 수십 개 변수의 통계적 패턴을 학습하여 Good과 Bad를 **대량으로** 분리한다. 전체 모집단을 한 번에 훑으며 리스크 서열을 매기는 것이 모형의 역할이다.
- **필터링룰** = **핀셋으로 하나씩 골라내기.** 모형이 다루기 어려운 **명확한 개별 리스크**("현재 연체 중", "명의 도용 의심" 등)를 단순한 규칙(if-then)으로 잡아낸다. 모형 전후에서 모형의 사각지대를 보완하는 역할이다.

[^filter-analogy]: 썩은 사과를 선별하는 공정에 빗댄 비유로, 현업에서 전해 듣고 재구성한 표현이다.

| | CSS 모형 | 필터링룰 |
|---|---|---|
| **대상** | 전체 모집단의 리스크 패턴 | 특정 조건에 해당하는 개별 건 |
| **방식** | 통계적·확률적 (연속 점수) | 규칙 기반 (if-then, 이분법) |
| **강점** | 다수 변수의 복합 효과를 한 번에 반영 | 명확한 거절 사유를 즉시·확실하게 포착 |
| **약점** | 희소 이벤트·정책 변경에 즉각 대응 어려움 | 변수 간 상호작용·미묘한 패턴 포착 불가 |

!!! tip "왜 모형만으로는 부족한가"
    CSS 모형은 **개발 시점의 데이터 패턴**을 학습한 결과물이다. 그런데 "현재 연체 중인 고객을 거절하라"는 것은 통계적 패턴이 아니라 **업무 규칙**이다. 이런 규칙은 모형에 녹이기보다 필터링룰로 분리하는 것이 관리·감사·변경 측면에서 훨씬 효율적이다. 규제 변경이나 새로운 사기 유형이 등장했을 때, 모형을 재개발하려면 수개월이 걸리지만 필터링룰은 즉시 추가·수정할 수 있다.

### 사전 필터링 (Pre-Screen)

CSS 모형에 투입하기 **전 단계**에서, 명확한 거절 사유가 있는 건을 사전에 걸러내는 과정이다. 모형 점수와 무관하게 자동 거절되므로, 심사 효율을 높이고 모형이 불필요한 리스크를 평가하는 것을 방지한다. 이 단계에는 제도적으로 대출 자격 자체가 없는 건(자격 요건 검증)과, 자격은 있으나 명백한 리스크 시그널로 모형 평가 없이 거절하는 건(리스크 기반 사전 거절)이 함께 포함된다.

자격 요건과 Bad 정의 수준의 상태(기불량)는 모형 개발 시의 [사전 제외 대상군](requirements.md)과 일치시켜야 한다. 개발 표본에는 없던 집단이 운영 중에 모형으로 들어오면, 그 집단에 대한 점수는 검증되지 않은 값이 된다. 반면 리스크 기반 거절 정책은 개발 표본에서 미리 지우지 않는다. 표본에 남겨야 정책이 바뀌어도 모형을 다시 만들지 않아도 되고, 그 정책이 실제로 불량률을 가르는지도 확인할 수 있다. 그런 신호로 거절할 때는 점수를 먼저 산출한 뒤 승인 정책 단계에서 거절하는 편이 낫다. 그래야 운영에서 점수가 나오는 집단이 개발 표본과 같아지고, 거절된 건의 점수 분포도 모니터링할 수 있다.

| 필터링 유형 | 예시 | 근거 |
|------|------|------|
| **법적·제도적 기준** | 미성년자, 금융거래 제한자, 제재 대상자(AML/KYC 위반) | 상품·제도상 대출 대상이 아님 |
| **신용 사고 이력** | Bad 정의 수준의 연체 진행 중, 채무불이행 등록 중, 회생·파산 진행 중 | 모형 점수와 무관하게 리스크가 확정적 |
| **내부 정책 기준** | 기존 대출 한도 초과, 동일인 중복 신청, 직원 대출 제한 | 기관 내부 여신 정책 위반 |
| **사기 탐지** | 명의 도용 의심, 이상 패턴 탐지(FDS Rule 기반) | 정상 거래가 아닌 건을 모형에 투입하면 점수 자체가 무의미 |

!!! example "사전 필터링 룰 예시"
    ```
    IF 현재_최장_연체일수 ≥ 90일      → 자동 거절 (사유코드: R01)
    IF 채무불이행_등록_중 = TRUE      → 자동 거절 (사유코드: R02)
    IF 본인인증_실패 = TRUE          → 자동 거절 (사유코드: R03)
    IF 신청자_연령 < 19세            → 자동 거절 (사유코드: R04)
    ```
    이 단계를 통과한 건만 CSS 모형에 투입된다.

### 사후 필터링 (Post-Screen)

CSS 모형 평가가 완료된 **이후 단계**에서, 모형 점수만으로는 반영되지 않는 추가 리스크 요인을 점검하는 과정이다. 모형 점수상 승인 대상이더라도 사후 필터에 걸리면 거절되거나 조건이 변경될 수 있다.

| 필터링 유형 | 예시 | 근거 |
|------|------|------|
| **총부채 관리** | DSR(총부채원리금상환비율) 기준 초과 여부 | 규제 기준은 모형 점수와 독립적으로 적용 |
| **담보·보증 검증** | 담보 감정가 대비 LTV 초과 여부 | 담보 가치는 모형 변수에 포함되지 않는 경우가 많음 |
| **업종·지역 제한** | 고위험 업종(유흥, 도박 등) 또는 특정 지역 제한 | 경영진의 포트폴리오 정책에 의한 제한 |
| **정성 심사** | 고액 건에 대한 심사역 재검토, 현장 실사 | 모형이 포착하지 못하는 정성적 리스크 요인 |
| **한도 조정** | 모형 점수 기준 한도와 DSR 기준 한도 중 작은 값 적용 | 모형 산출 한도와 규제 한도의 교차 검증 |
| **등급 상한** | 단기 연체 진행 중, 대표자 개인의 신용 사고 등 항목별로 받을 수 있는 최고 등급을 제한 | 발생은 드물지만 위험이 매우 높은 신호를 모형 밖에서 반영. 상세는 [등급 상한](../part5_scorecard/scorecard-and-rating.md) |

!!! example "사후 필터링 룰 예시"
    ```
    IF DSR > 적용 DSR 한도              → 거절 또는 한도 축소 (사유코드: P01)
    IF LTV > 지역·주택 보유수별 LTV 한도 → 한도 축소 (사유코드: P02)
    IF 대출금액 ≥ 1억원                 → 심사역 수동 재검토 (사유코드: P03)
    IF 업종코드 ∈ {고위험 업종 목록}     → 거절 (사유코드: P04)
    ```
    사후 필터링은 거절뿐 아니라 **조건 변경**(한도 축소, 금리 상향)으로 이어지기도 한다. DSR·LTV 한도는 업권·지역·시기별 규제에 따라 달라지므로 룰에는 고정 숫자 대신 별도 기준표를 참조하게 두는 것이 일반적이다.

### 전체 프로세스 흐름

> **Pre-Screen** (사전 필터링, 자동 거절) → **CSS 모형 평가** (점수 산출) → **Post-Screen** (사후 필터링, DSR·담보·정성) → **최종 의사결정** (승인·한도·금리 확정)

!!! note "모형의 역할 범위"
    CSS 모형은 여신 의사결정 프로세스의 **핵심 구성요소**이지만, 유일한 판단 도구가 아니다. 사전·사후 필터링, 정책 규칙(Policy Rule), 심사역 판단이 모형 점수와 결합되어 최종 의사결정이 이루어진다. 모형 개발자는 이 전체 프로세스 속에서 모형이 담당하는 역할과 한계를 명확히 인식해야 한다.

!!! note "필터링룰의 관리"
    필터링룰은 모형과 달리 **별도의 룰 엔진(Rule Engine)**에서 관리되는 것이 일반적이다. 룰 변경은 모형 재개발 없이도 가능하며, 규제 변경·신종 사기 대응 등 **빠른 반영이 필요한 상황**에서 핵심적인 유연성을 제공한다. 다만, 룰이 과도하게 누적되면 모형의 변별력과 충돌하거나 승인율을 불필요하게 떨어뜨릴 수 있으므로, 정기적으로 룰의 적중률과 영향도를 모니터링하여 정비해야 한다. 룰로 거절되는 건은 성과가 관측되지 않으므로, 다음 모형 개발 때 [거절추론](requirements.md) 대상이 된다는 점도 고려한다.

!!! warning "모형과 룰에 같은 신호를 쓸 때"
    같은 신호를 모형 변수와 룰(필터링, 등급 상한)에 모두 쓰면 한 차주가 두 번 불이익을 받는다. 이것은 금지 사항이 아니라 설계 선택이다. 최종 모형의 변수와 룰의 원천을 한 표로 대조해, 룰마다 그 정보가 모형에 어떻게 들어갔는지(직접 투입, 합성항목의 재료, 같은 집계의 다른 기간, 미사용)를 표시한다. 겹치는 룰은 상한을 관대하게 두어 바닥 역할만 하게 하고, 결합 등급을 낸 뒤 상위 등급에 부실 차주가 남는지 보고 채택 여부를 정한다. "최근 N개월 최장 연체일수" 같은 항목은 진행 중인 연체도 함께 세므로, 미해제 연체 항목을 모형에서 뺐다고 해서 그 신호가 모형에서 사라지지는 않는다.

!!! tip "단일 의사결정나무를 활용한 룰 도출"
    필터링룰을 데이터 기반으로 도출하는 방법으로 단일 의사결정나무가 활용되기도 한다. 자세한 내용은 [Part 3 — 단일 트리의 실무 활용: 룰 기반 시스템](../../ml/part3_tree_ensemble/tree_models.md#17)을 참고한다.
