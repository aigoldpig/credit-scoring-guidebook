# 피처 선택 · 파생변수

## 7.1 피처 선택 (Feature Selection)

### 출발점은 단변량 분석이다

ML 모형이라고 해서 변수를 무작정 넣고 Feature Importance만 보는 것은 아니다. **개별 변수의 유의성과 타당성을 먼저 확인**하는 것이 출발점이다.

저자의 경우, ML 기반 모델링에서도 후보 변수에 대해 **binning(구간화)**을 수행한다. 구간별 Bad Rate 패턴을 눈으로 확인하면, 그 변수가 타겟과 어떤 관계를 가지는지 — 단조적인지, 비선형인지, 특정 구간에서만 유효한지 — 를 직관적으로 파악할 수 있다. 이 과정은 전통 스코어카드의 Fine Classing과 본질적으로 같다.

이렇게 하는 이유는 두 가지다.

1. **도메인 타당성 검증**: Feature Importance가 높더라도, 변수의 패턴이 비즈니스 로직에 반하면 투입해서는 안 된다. binning을 통해 "이 변수가 왜 유의한지"를 사전에 이해하고 설명할 수 있어야 한다.
2. **노이즈 변수 사전 제거**: IV가 극히 낮거나 패턴이 불안정한 변수를 미리 걸러두면, 이후 ML 학습의 효율성과 안정성이 높아진다.

단변량 분석으로 후보 풀을 정리한 뒤에, 변수 간 **교호작용(interaction) 탐색**을 거쳐, ML 기반 중요도 지표들을 활용하여 최종 변수를 선별한다.

### 2-way Interaction 탐색 — Joint IV

단변량 스크리닝으로 50~100개의 좋은 후보를 추렸다면, 그다음으로 확인할 것은 **변수 간 교호작용**이다. 변수 A 단독으로는 변별력이 보통이지만, 변수 B와 조합하면 특정 세그먼트에서 불량률이 급격히 달라지는 경우가 있다. 이런 조합 효과를 사전에 파악하면 변수 선정의 질이 높아진다.

가장 직관적인 방법은 **Joint IV**다:

| 개념 | 정의 | 의미 |
|---|---|---|
| 단변량 IV(X1) | X1 단독의 Information Value | X1 혼자의 변별력 |
| 단변량 IV(X2) | X2 단독의 Information Value | X2 혼자의 변별력 |
| Joint IV(X1, X2) | X1 × X2 cross-tabulation의 IV | 두 변수 조합의 총 변별력 |
| Marginal IV | Joint IV(X1, X2) − IV(X1) | **X1에 X2를 조합해서 얻는 추가 변별력** |

Marginal IV가 크다는 것은, X2가 X1과 결합했을 때 X1 단독 대비 **추가 정보를 제공**한다는 뜻이다.

!!! warning "Marginal IV는 칸 수가 많을수록 부풀려진다"
    교차표는 X1의 구간을 더 잘게 나눈 것이므로, Joint IV는 이론적으로 IV(X1)보다 작아질 수 없다. 따라서 Marginal IV는 **항상 0 이상**이다. 게다가 표본에서 계산한 IV는 구간(칸)이 많고 칸당 건수가 적을수록 우연한 불량률 차이 때문에 커지는 편향이 있다. X1이 5구간, X2가 5구간이면 교차표는 25칸이 되므로, 아무 관계가 없는 X2를 붙여도 Marginal IV가 0보다 크게 나온다.

    그래서 Marginal IV는 절대값보다 **상대 비교**로 쓰고, 칸당 최소 건수(특히 Bad 건수)를 정해 두며, 필요하면 X2의 값을 무작위로 섞어 계산한 Marginal IV(순열 기준선)와 비교해 "우연으로도 이 정도는 나온다"는 수준을 확인한다.

Joint IV의 "추가 정보" 안에는 실제로 두 가지가 섞여 있다: **(1)** X2의 **고유 main effect**(X1이 못 잡는 별도 패턴)와, **(2)** X1 × X2의 **순수 interaction**(두 변수가 동시에 특정 조합일 때만 나타나는 효과). Joint IV는 이 둘을 구분하지 않고 총량만 측정하지만, 변수 탐색 단계에서는 총량만으로 충분하다 — **"추가 정보가 있는가?"**가 중요하지, 그것이 main인지 interaction인지는 변수 선정 시점에서는 부차적이다.

!!! info "EBM의 FAST 알고리즘과 닮은 점, 다른 점"
    EBM(GA²M)이 interaction 쌍을 찾을 때 사용하는 **FAST 알고리즘**(Lou et al., KDD 2013)도 "개별 효과를 먼저 보고, 그 위에 조합 효과를 측정"하는 2-stage 사상을 따른다는 점에서 Joint IV와 닮았다.

    | | Joint IV 방식 | FAST 알고리즘 |
    |---|---|---|
    | **1단계** | 단변량 IV로 변수 선정 | 모든 변수의 main effect를 가법 모형으로 먼저 학습 |
    | **2단계** | X1 × Xi의 Joint IV 계산 | main effect 모형의 **잔차**에 각 쌍별로 2×2 격자 적합 |
    | **3단계** | Marginal IV가 큰 쌍 선정 | 잔차 RSS 감소량이 큰 쌍 선정 |

    결정적인 차이가 있다. FAST는 **모든 변수의 main effect를 제거한 잔차**에서 측정하므로 순수 교호작용에 가까운 양을 본다. 반면 Joint IV의 추가분에는 아래 설명처럼 X2 자체의 main effect가 섞여 있다. Joint IV는 "추가 정보가 있는가"를 빠르게 보는 탐색 도구이고, 교호작용 자체를 분리하려면 FAST 같은 잔차 기반 접근이 필요하다.

#### 단일 Decision Tree로 조합을 찾으면 안 되는가

변수가 많을 때, 단일 decision tree(depth 3~4)를 적합하면 greedy search로 좋은 변수 쌍을 자동으로 찾아줄 것 같다. **그러나 문제가 있다.** 핵심 변수 X1의 main effect가 압도적으로 크면, 트리가 X1으로만 반복 분기한다:

```
X1 > 100?
├── X1 > 200?
│   ├── X1 > 300?      ← X1만 3번 연속 분기
│   └── ...
└── X1 > 50?
    └── ...
```

X1의 구간을 더 세밀하게 쪼개는 것이 불순도(분류 트리라면 Gini·Entropy) 감소가 가장 크기 때문이다. 이러면 X2, X3와의 interaction은 아예 나타나지 않는다. 또한, 트리에서 X1 다음에 X2가 분기된다고 해서 반드시 interaction은 아니다 — X2의 main effect가 강해서 **어디서든** 분기될 수 있다. 진짜 interaction은 "X1의 값에 따라 X2의 효과가 **달라지는** 것"인데, 단일 트리의 분기 구조만으로는 이 구분이 어렵다.

결론: 단일 트리는 main effect와 interaction을 구분하지 못한다. 이 구분을 하려면 잔차 기반 접근(= main effect를 먼저 제거하고 남은 것을 보는 것, 위 FAST 알고리즘)이 필요하다. Joint IV는 X2의 고유 main effect와 순수 interaction을 합친 추가 정보의 양만 보여 준다.

### Feature Importance (Split 기반)

트리 앙상블이 학습 과정에서 자연스럽게 산출하는 변수 중요도다.

| 지표 | 의미 |
|------|------|
| **Split count (Frequency)** | 해당 변수가 분할에 사용된 횟수 |
| **Gain** | 해당 변수의 분할이 가져온 loss 감소량의 합 |
| **Coverage** | 해당 변수의 분할이 영향을 미친 샘플 수 |

!!! warning "Split 기반 중요도의 함정"
    카디널리티가 높은 변수(예: 우편번호, 고유값이 많은 금액 변수)는 분할 후보가 많아서 **split 횟수가 부풀려진다**. Gain 기반 중요도도 이 편향에서 자유롭지 않다. 후보가 많을수록 우연히 큰 gain을 내는 분할을 찾을 가능성이 커지기 때문이다(Strobl et al., 2007). 또 split 기반 중요도는 **학습셋**에서 계산되므로 과적합된 분할의 gain도 그대로 반영된다. 그래서 split 기반 중요도는 1차 참고로만 쓰고, 검증셋 기반 지표(Permutation)나 SHAP과 교차 확인한다.

### Permutation Importance

변수의 값을 **무작위로 섞은 뒤** 성능이 얼마나 떨어지는지로 중요도를 측정한다.

| 장점 | 단점 |
|------|------|
| 어떤 모형에도 적용 가능 (model-agnostic) | 상관된 변수 중 하나만 섞으면 현실에 없는 조합(예: 고소득인데 소득 관련 다른 변수는 저소득 수준)이 만들어져 결과가 왜곡될 수 있음 |
| 검증셋에서 계산하면 과적합된 분할의 영향을 덜 받음 | 변수 수 × 반복 횟수만큼 연산 필요 |
| 해석이 직관적 ("이 변수를 망가뜨리면 AR이 얼마나 떨어지나") | 교호작용 효과가 관련된 각 변수의 중요도에 중복 반영됨 |

### SHAP 기반 피처 선택

[SHAP](../part4_interpretation/interpretability.md)의 평균 절대값 \(\text{mean}(|\phi_j|)\)으로 변수 중요도를 측정한다.

SHAP 기반 중요도는 개별 예측의 기여도를 공리적으로 분배한 값을 모은 것이라, 방향(+/−)과 개인별 분포까지 볼 수 있다는 장점이 있다. 그러나 다른 중요도 지표와 마찬가지로 **학습된 모형이 무엇을 썼는지**를 설명할 뿐, 데이터 속 변수의 "진짜 중요도"를 알려주지는 않는다. 모형이 한 번도 분할에 쓰지 않은 변수는 TreeSHAP 값이 모든 관측치에서 정확히 0이다. 상관이 높은 변수들 사이에서 SHAP 값이 어떻게 나뉘는지는 모형이 그 변수들을 어떻게 나눠 썼는지, 그리고 SHAP의 기댓값을 어떤 방식으로 계산하는지에 따라 달라진다. 이 문제는 [부록 B. 변수 상관과 모형 해석](../appendix/correlation-interpretation/index.md)에서 다룬다.

!!! tip "실무에서의 피처 선택 전략"
    하나의 방법에 의존하기보다, **여러 방법의 결과를 종합**하는 것이 안전하다.

    1. **1차 스크리닝**: Gain 기반 Feature Importance나 SHAP 중요도로 하위 변수 후보 표시
    2. **2차 검증**: 검증셋 Permutation Importance로 교차 확인 (상관 변수는 그룹 단위로 섞어 보기)
    3. **최종 해석**: SHAP Summary Plot으로 선택된 변수의 방향성·패턴 검증
    4. **도메인 판단**: 통계적으로 유의하더라도 비즈니스 로직에 반하는 변수는 제외

### Boruta — "무작위 변수보다 나은가"를 묻는 방법

Boruta(Kursa & Rudnicki, *Journal of Statistical Software*, 2010)는 중요도의 **기준선**을 데이터에서 직접 만드는 변수 선택 방법이다.

1. 각 원래 변수를 복사한 뒤 값을 무작위로 섞은 **그림자 변수(shadow feature)**를 만든다. 그림자 변수는 원래 변수와 분포는 같지만 타겟과의 관계는 끊겨 있다.
2. 원래 변수와 그림자 변수를 함께 넣어 Random Forest(또는 다른 트리 앙상블)를 적합하고 중요도를 계산한다.
3. 각 원래 변수의 중요도가 **그림자 변수 중 최댓값**보다 높은지 기록한다.
4. 이를 여러 번 반복해, 그림자 최댓값을 통계적으로 유의하게 이기는 변수는 **확정(Confirmed)**, 유의하게 지는 변수는 **기각(Rejected)**, 판정이 안 나는 변수는 **보류(Tentative)**로 분류한다.

| 장점 | 한계 |
|---|---|
| "중요도 몇 이상이면 남긴다" 같은 임의 기준 없이, 무작위 변수라는 객관적 기준선을 쓴다 | 반복 적합이 필요해 연산 비용이 크다 |
| 약하지만 실제로 관계가 있는 변수까지 모두 찾는 **all-relevant** 방식이다 | 중복 변수(상관 높은 변수 쌍)를 둘 다 확정하는 경향이 있어, 변수 수를 줄이는 목적에는 상관 정리가 별도로 필요하다 |
| 모형 중요도의 우연한 변동을 반복으로 걸러 낸다 | 내부 중요도 지표(예: split 기반)의 편향을 그대로 물려받는다 |

신용평가에서는 수백 개 후보 변수 중 **명백히 무의미한 변수를 걸러 내는 1차 필터**로 쓰기 좋다. 최종 변수 수를 줄이는 일은 아래의 하위 제거 시뮬레이션과 도메인 판단으로 마무리한다.

### 중요도가 0인 변수의 원인

Global Feature Importance — TreeSHAP의 \(\text{mean}(|\phi_j|)\), Permutation Importance, Split 기반 Gain — 에서 중요도가 **정확히 0**으로 나오는 변수가 있다. 이런 변수는 세 가지 원인으로 분류된다.

| 원인 | 설명 | 예시 |
|------|------|------|
| **진짜 무의미** | 타겟과 아무 통계적 관계가 없는 변수. 전체 트리에서 한 번도 split에 사용되지 않음 | 고객 ID, 랜덤 노이즈, 의미 없는 코드값 |
| **다중공선성 (Redundancy)** | 더 나은 상관 변수에 밀려서 선택되지 못한 변수. 단독으로는 유의미하지만 상위 변수가 이미 같은 정보를 흡수 | DSR과 상관계수 0.95인 DSR 변형 변수(기준월만 다른 DSR 등) |
| **분할 문턱에 걸림** | 분할 이득이 최소 기준(`gamma`, 최소 분할 이득)을 넘지 못하거나, 분할 후 리프가 최소 건수·최소 hessian 합(`min_child_weight`) 기준을 채우지 못해 한 번도 채택되지 않음. 트리 수가 적거나 학습률이 작아 학습이 일찍 끝나도 약한 변수까지 차례가 오지 않음 | 수백 개 변수 중 효과가 아주 작은 변수 |

!!! warning "0 = 쓰레기가 아닐 수 있다"
    두 번째 원인(다중공선성)이 실무에서 특히 중요하다. A 변수와 B 변수의 상관이 매우 높을 때, 모든 split에서 A가 미세하게 더 나으면 B의 importance는 0에 수렴한다. 그러나 **A를 제거하면 B가 그 역할을 대체**한다. 이런 변수를 "무의미"로 판단하면 안 된다.

    중요도 0인 변수를 제거할 때는, 단순히 importance 값만 볼 것이 아니라 **상관 변수 그룹 내에서의 역할**을 함께 확인하는 것이 안전하다.

    참고로 `colsample_bytree`(XGBoost)나 `max_features`(Random Forest) 같은 **변수 서브샘플링은 오히려 약한 변수에 기회를 준다**. 강한 변수가 후보에서 빠진 트리에서는 그다음 변수가 선택되기 때문이다. 서브샘플링을 켜면 상관 변수들 사이에 중요도가 나뉘어 퍼지는 경향이 생긴다.

### 중요도 기반 변수 제거 전략

실무에서는 단변량 분석과 ML 기반 중요도를 **2단계로 결합**하여 변수를 정리한다.

**1단계 — 단변량 스크리닝**

전통적 변수 선정 프로세스(IV, 단변량 LR 등)를 통과한 변수만 ML 모형의 후보로 투입한다. 이 단계에서 타겟과 무관한 변수, 안정성이 낮은 변수(PSI 기준), 비즈니스 로직에 반하는 변수가 사전에 걸러진다.

!!! info "전통 스코어카드 변수 선정과의 차이"
    1단계 스크리닝 자체는 전통 스코어카드와 크게 다르지 않다 — IV 기준으로 변별력을 보고, PSI로 안정성을 체크하는 흐름은 동일하다. 다만 두 가지 점에서 **에너지 배분이 달라진다.**

    - **성능만 보면 상관분석을 느슨하게 해도 된다**: 로지스틱 회귀에서는 다중공선성이 β 추정을 불안정하게 만들므로 상관이 높은 변수를 엄격히 걸러야 했다([Part 4 참조](../../scorecard/part4_modeling/multivariate-regression.md)). 트리 앙상블은 상관된 변수를 투입해도 예측 성능이 크게 흔들리지 않으므로, "일단 넣고 모형이 알아서 선택하게" 하는 전략이 가능하다. **단, 해석은 다르다.** 상관된 변수들이 함께 들어가면 어느 변수에 기여도가 몰릴지가 학습마다 달라지고, 한 변수의 SHAP 방향이 상식과 반대로 보이는 일도 생긴다. 해석과 설명이 필요한 모형이라면 상관 변수 정리를 생략하지 않는 편이 낫다([부록 B. 변수 상관과 모형 해석](../appendix/correlation-interpretation/index.md)).
    - **WoE 변환에 시간을 쏟지 않는다**: 전통 스코어카드에서 가장 노동 집약적인 단계가 Fine/Coarse Classing → WoE 변환이었다. ML에서는 이 과정이 구조적으로 불필요하므로, 1단계에서는 IV 등으로 **변별력만 빠르게 확인**하고 넘어간다.

**2단계 — ML Importance 기반 하위 제거 시뮬레이션**

1단계를 통과한 변수로 ML 모형을 학습한 뒤, **중요도 하위 n%를 제거하면서 성능 변화를 관찰**한다. 학습셋에서 계산한 SHAP 기반 중요도로 변수를 정렬하고, 하위부터 순차적으로 제거해 재학습하면서 **검증셋** AR(필요하면 KS도)의 변화를 추적하는 방식이다. 이 과정 자체가 검증셋을 여러 번 보는 선택 과정이므로, 최종 성능은 별도 Test/OOT에서 확인한다.

전형적인 결과 패턴(시뮬레이션 참조값):

```
Drop  0% → 150개 변수, 검증 AR=0.5646
Drop  1% → 149개 변수, 검증 AR=0.5646   ← 변화 없음
Drop  5% → 143개 변수, 검증 AR=0.5642   ← 거의 동일
Drop 10% → 135개 변수, 검증 AR=0.5636   ← 미미한 하락
Drop 15% → 128개 변수, 검증 AR=0.5610   ← 하락 시작
Drop 20% → 120개 변수, 검증 AR=0.5560   ← 유의미한 하락
```

이 결과에서 **성능 하락이 시작되는 지점 직전**이 최적 제거 비율이 된다. 위 예시에서는 하위 10%까지는 제거해도 무방하다고 판단할 수 있다. 0.001 수준의 차이는 데이터 분할이나 시드만 바꿔도 생기는 변동일 수 있으므로, 가능하면 여러 시드나 CV로 변동 폭을 함께 본다.

!!! tip "변수를 줄이는 것의 실무적 가치"
    검증 성능(KS·AR)이 사실상 같다면, 변수가 적은 모형이 **거의 항상** 낫다.

    - **운영 비용 절감**: 모형에 투입되는 변수 수 = 데이터 파이프라인에서 관리해야 할 변수 수
    - **모니터링 부담 감소**: 변수별 PSI 모니터링, 결측률 관리 등의 부담이 줄어든다
    - **안정성 향상**: 불필요한 변수가 향후 데이터 분포 변화에 의해 노이즈를 유입할 가능성을 사전 차단

### Importance 유형 간 차이에 대한 주의

동일한 변수라도 **어떤 중요도 지표를 사용하느냐**에 따라 결과가 달라질 수 있다.

| 지표 | 무엇을 재는가 | 중요도 0의 의미 |
|------|----------------|----------------|
| **Split Gain** | 학습 중 그 변수의 분할이 줄인 손실의 합 (학습셋 기준) | 한 번도 split에 사용되지 않음 |
| **Permutation Importance** | 그 변수를 섞었을 때 성능(예: 검증 AR)이 떨어지는 정도 | 섞어도 모형 성능이 변하지 않음 |
| **SHAP \(\text{mean}(\|\phi_j\|)\)** | 개별 예측에 대한 그 변수의 기여 크기의 평균 | 어떤 예측에도 기여하지 않음 (TreeSHAP에서는 분할에 한 번도 안 쓰인 변수) |

세 지표 모두 **학습된 모형이 그 변수를 얼마나 썼는가**를 잰다. 데이터 속에서 변수가 타겟과 얼마나 관련 있는지를 재는 지표가 아니다. 상관이 높은 변수 A, B가 있을 때 결과는 "모형이 A와 B를 어떻게 나눠 썼는가"에 따라 갈린다.

!!! example "같은 데이터, 모형의 사용 방식에 따라 다른 결과"
    A와 B의 상관이 매우 높다고 하자.

    **경우 1 — 모형이 A만 쓴 경우** (부스팅에서 모든 분할마다 A가 미세하게 더 나아 B가 한 번도 선택되지 않음)

    - **Split Gain**: A = 높음, B = 0
    - **Permutation**: A = 높음, B = 0 (모형이 B를 쓰지 않으므로 B를 섞어도 예측이 그대로)
    - **SHAP**: A = 높음, B = 0 (TreeSHAP에서 모형이 쓰지 않은 변수의 기여는 정확히 0)

    **경우 2 — 모형이 A와 B를 나눠 쓴 경우** (Random Forest의 변수 서브샘플링 등)

    - **Split Gain**: A·B 모두 중간 (분할을 나눠 가짐)
    - **Permutation**: A·B 모두 낮을 수 있음 (하나를 섞어도 다른 하나가 상당 부분을 보상)
    - **SHAP**: A·B 모두 중간 (기여가 두 변수에 나뉨)

    어느 경우든 "B의 중요도가 낮다 = B가 정보가 없다"는 결론은 틀릴 수 있다. A를 빼고 재학습하면 B가 그 역할을 대신한다. 따라서 중요도가 낮은 변수를 지울 때는 **상관 변수 그룹 단위로** 판단하고, 그룹을 통째로 빼거나 섞어 보는 방식(그룹 Permutation)으로 그룹의 정보량을 확인하는 것이 안전하다. 상관 변수와 SHAP의 관계는 [부록 B](../appendix/correlation-interpretation/index.md)에서 자세히 다룬다.

## 7.2 파생변수 생성 (Interaction Feature Engineering)

트리 모형은 depth ≥ 2에서 변수 간 교호작용(interaction)을 자동으로 학습한다. 그럼에도 불구하고, **명시적 파생변수**를 만들어 투입하면 성능이 개선되는 경우가 있다.

### 실무에서 자주 쓰는 파생변수 유형

무작위로 변수를 곱하거나 나누는 전수탐색보다, **도메인 논리에 기반한 파생변수**가 실무에서 훨씬 효과적이다. 특히 많이 쓰이는 유형은 **비율/비중**과 **증감률** 두 가지다.

#### (1) 비율 / 비중

전체 대비 특정 항목의 비중을 계산하는 변수다.

$$
\text{비중}(\%) = \frac{\text{부분 금액}}{\text{전체 금액}} \times 100
$$

| 파생변수 | 산식 | 범위 | 의미 |
|---------|------|:----:|------|
| **현금서비스 비중** | 현금서비스 이용액 / 카드 총 이용액 × 100 | 0~100% | 카드 이용 중 단기 유동성 의존도 |
| **이용률** (Utilization) | 카드 사용액 / 한도 × 100 | 0~100% (한도 초과 시 100% 초과 가능) | 신용 여력 소진 정도 |
| **DSR** (총부채원리금상환비율) | 모든 대출의 연간 원리금 상환액 / 연 소득 × 100 | 0~∞ | 소득 대비 상환 부담 |

DTI(총부채상환비율)는 주택담보대출 원리금 상환액에 기타 대출의 **이자** 상환액만 더해 연 소득으로 나눈 값이고, DSR은 모든 대출의 **원리금**을 반영한다. "총부채 / 연 소득"은 DTI가 아니라 소득 대비 부채 잔액 배수(LTI 성격)다. 같은 "부채 부담" 변수라도 정의가 다르면 분포와 의미가 달라지므로, 파생변수 명세서에 산식을 정확히 남겨야 한다.

#### (2) 증감률

과거 대비 현재의 변화율을 측정하는 변수다.

$$
\text{증감률}(\%) = \frac{\text{현재 금액} - \text{과거 금액}}{\text{과거 금액}} \times 100
$$

| 파생변수 | 산식 | 범위 | 의미 |
|---------|------|:----:|------|
| **카드사용 증감률** | (올해 사용액 - 작년 사용액) / 작년 사용액 × 100 | -100% ~ ∞ | 소비 패턴 변화 |
| **소득 증감률** | (현재 소득 - 전년 소득) / 전년 소득 × 100 | -100% ~ ∞ | 소득 안정성 |

증감률은 이론적으로 상한이 없으므로(예: 10만 원 → 1,000만 원이면 +9,900%), 실무에서는 **상한선(upper limit)을 설정**하여 capping한다.

#### 분모가 0인 경우의 처리

비율과 증감률 모두 **분모가 0이면 정의되지 않는다**. 이 경우의 처리가 파생변수 설계에서 가장 까다로운 부분이다.

| 상황 | 예시 | 처리 방법 |
|------|------|----------|
| **분모 = 0, 분자 = 0** | 작년 사용액 0, 올해 사용액 0 | 0%(변화 없음)로 두기 쉽지만 상품 미사용 상태라 0% 변화와 의미가 다르다. **별도 특수값**으로 두고 귀속 구간은 실측 불량률로 정한다 |
| **분모 = 0, 분자 > 0** | 작년 사용액 0, 올해 사용액 100만 | **특이치(Special Value)로 정의** — 별도 코드 부여 |
| **분모 = 0, 분자 < 0** | (해당되는 경우) | 위와 동일하게 특이치 처리 |

!!! warning "특이치 정의를 상세하게 해야 한다"
    "분모가 0이면 NaN으로 처리"는 가장 위험한 접근이다. **"작년에 카드를 전혀 안 쓰다가 올해 처음 쓰기 시작한 고객"**은 리스크 관점에서 매우 의미 있는 세그먼트다. 이를 결측으로 날려버리면 중요한 정보가 소실된다.

    실무에서는 분모 0인 케이스를 **별도 범주(Special Value)**로 정의하고, 해당 범주의 Bad Rate를 확인하여 모형에서 독립적으로 취급한다. 트리 모형에서는 이 Special Value가 자연스럽게 별도 리프로 분리된다.

### 기타 파생변수 유형

| 유형 | 예시 | 의미 |
|------|------|------|
| **차이** | 소득 - 월 상환액 | 가처분 소득 (순 효과 포착) |
| **곱** | 연체 횟수 × 평균 연체 금액 | 연체의 빈도와 규모를 동시에 반영 |
| **조건부 조합** | 연체 횟수 × (대출 잔액 > 0) | 특정 조건하의 효과 |

이 유형들도 유용하지만, 비율/증감률 대비 활용 빈도는 낮다.

### 자동 탐색보다 도메인 설계가 우선이다

모든 변수 쌍에 대해 곱/나눗셈을 전수탐색하는 방식이 있지만, 실무에서는 효과가 제한적이다.

| 한계 | 설명 |
|------|------|
| **트리가 이미 잡는다** | depth ≥ 2면 변수 간 조건부 분기를 자동으로 학습 — 명시적 파생변수가 없어도 됨 |
| **노이즈 변수 증가** | 수천 개의 파생변수 중 대부분은 무의미 |
| **도메인 논리 부재** | "왜 이 조합이 의미 있는가"를 설명할 수 없으면, 모형 검증에서 걸린다 |

!!! tip "파생변수 생성 원칙"

    1. **도메인 논리가 먼저**: "이 비율이 왜 리스크와 관련되는가?"를 설명할 수 있어야 한다
    2. **분모 0 처리를 명확히**: 특이치 정의 없이 파생변수를 만들면 NaN이 폭발한다
    3. **트리의 능력을 신뢰**: depth가 충분하면 대부분의 interaction은 모형이 알아서 학습한다
    4. **변수 수 관리**: 파생변수를 무분별하게 추가하면 모니터링·운영 부담이 증가한다

## 7.3 전통 스코어카드 vs 트리 모형의 전처리 요약

| 단계 | 전통 스코어카드 | 트리 앙상블 |
|------|---------------|------------|
| **구간화** | Fine → Coarse Classing (수작업) | **불필요** — 트리 split이 대체 |
| **변별력 측정** | WoE/IV | Feature Importance / SHAP |
| **범주형 처리** | WoE 변환 | Label / Target / Native Categorical |
| **결측치** | 별도 구간화 | XGB/LGBM 자동 처리 |
| **이상치** | Capping + 구간 경계 조정 | 대부분 자동 분리 (float32 예외 주의) |
| **스케일링** | WoE가 스케일 통일 | **불필요** — 순서만 보는 구조 |
| **변수 선택** | IV 기준 → 단변량 LR → 정보영역별 | Importance → Permutation → SHAP |
| **소요 시간** | 변수당 수십 분 (수동 검토) | 자동화 가능 — 수백 개 변수를 분 단위로 처리 |

!!! warning "변수 수백 개를 한꺼번에? — 전문 길이 제한"
    학술 논문이나 Kaggle에서는 변수를 수백 개씩 넣어 학습하지만, **금융기관 ↔ CB사 간 실시간 스코어링 환경에서는 변수 개수에 물리적 제약**이 있다.

    신용조회 전문(API)은 **고정 길이 프로토콜**로 주고받는 경우가 많고, 전문 한 건의 최대 길이가 정해져 있다. 변수 하나를 추가하면 전문 필드가 늘어나므로, 모형이 아무리 좋아도 **전문 규격에 맞지 않으면 배포할 수 없다.**

    실무적 결과:

    - 모형 개발 시점부터 **사용 가능한 변수 풀(pool)이 전문 규격으로 제한**됨
    - 변수 추가/변경 시 전문 규격 변경 → 양사 간 협의 + 시스템 개발 필요
    - ML 모형이 수백 개 변수를 자유롭게 쓸 수 있다는 전제는 **CB 전문 규격에 구애받지 않는 Batch 환경(행동 스코어링, 사후 심사 등)에서 주로 성립**

    결국 "좋은 변수가 좋은 모형을 만든다"의 전제에는 **"쓸 수 있는 변수"의 물리적 한계**도 포함된다.
